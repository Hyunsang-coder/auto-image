가이드

AI 에이전트가 App Store 스크린샷을 편집하게 하기

Screenshot Studio는 MCP를 지원합니다. Claude Code를 비롯한 MCP 클라이언트를 연결하면, 지금 열어 둔 프로젝트를 에이전트가 직접 읽고, 모든 캡션을 번역하고, 헤드라인을 옮기고, 렌더링된 결과를 눈으로 확인하며 스스로 검토합니다. 그 동안 앱은 계속 눈앞에 있습니다 — 에이전트가 수정하는 대로 캔버스가 다시 그려지고, 보고 있던 슬라이드는 그대로 유지됩니다.

준비물

  • 실행 중인 Mac 앱 — 아직 없다면 여기서 내려받으세요.
  • Node 20 이상 (npx 실행용).
  • MCP 클라이언트: Claude Code, Claude Desktop, 그 밖에 프로토콜을 지원하는 도구면 무엇이든.

연결하기

Claude Code라면 명령 한 줄입니다:

claude mcp add screenshot-studio -- npx -y screenshot-studio-mcp

JSON 설정을 쓰는 클라이언트(Claude Desktop 등)라면:

{
  "mcpServers": {
    "screenshot-studio": {
      "command": "npx",
      "args": ["-y", "screenshot-studio-mcp"]
    }
  }
}

둘 다 앱 안에서 한 번의 클릭으로 얻을 수 있습니다. 헤더의 MCP 칩을 누르면 설정 복사와 Claude Code 명령 복사 버튼이 있는 카드가 열립니다.

그다음 에이전트에게 live_status를 호출해 보라고 하세요. 앱이 무엇을 열어 두고 있는지 — 단계, 프로젝트 이름, 슬라이드 수, 언어 — 를 답해 줍니다. 앱이 실행 중이 아니라고 하면 앱을 켜거나(아래의 스위치도 확인) 다시 물어보세요.

에이전트가 할 수 있는 일

도구하는 일
live_status앱이 실행 중인지, 무엇을 열어 두고 있는지 확인합니다.
live_focus특정 단계·슬라이드로 화면을 옮깁니다. 데이터는 바뀌지 않습니다.
live_new_project빈 프로젝트를 만들고 에디터로 이동합니다.
live_inspect열린 프로젝트를 간결한 JSON으로 읽습니다 — 슬라이드별 템플릿, 기기, 필드 주소가 붙은 텍스트·배지, 외부 이미지, 구조적 문제.
live_list_untranslated현지화 작업 목록: 아직 비어 있는 언어가 있는 모든 문자열을 원문·주소와 함께.
live_patch문구, 위치, 스타일, 배경, 기기 프레임, 배지, 하이라이트, 장식, 도형, 외부 이미지를 국소적으로 수정합니다.
live_view슬라이드 하나를 내보내기 해상도로 렌더링해 이미지로 돌려줍니다. 에이전트가 결과를 직접 봅니다.
live_save열린 프로젝트를 자기 .studio.zip 파일에 씁니다 — ⌘S와 같은 동작입니다.
live_open디스크의 .studio.zip을 지금 편집 중인 문서로 엽니다.
get_design_reference테마 id, 폰트, 레이아웃, 장식, 언어, 기기 모델과 내보내기 규격, 슬라이드별 한도.
get_patch_spec / get_import_spec패치 op 어휘와 매니페스트 작성 명세.

이렇게 시켜 보세요

1. 전체 번역

“비어 있는 캡션을 전부 일본어와 독일어로 번역해 줘.” 에이전트가 live_list_untranslated로 목록을 받아 번역한 뒤 live_patch로 써 넣고, 현지화 표가 그 자리에서 채워집니다. 프로젝트에 아직 선택돼 있지 않은 언어는 자동으로 추가됩니다. CSV를 내보내고 다시 가져올 필요가 없습니다.

2. 보고 고치기

“3번 슬라이드 헤드라인이 기기랑 겹쳐 — 고쳐 줘.” live_view는 실제 내보내기 규격으로 렌더링하므로, 에이전트는 실제로 출고될 레이아웃을 보고 판단하고, 수정한 뒤 다시 확인합니다.

3. 작업이 끝나면 저장

Mac에서는 프로젝트가 곧 파일입니다. 에이전트의 패치도 직접 편집한 것과 똑같이 문서를 수정된 상태로 만들 뿐 자동 저장되지 않으므로, “전부 번역하고 저장해 줘”는 마지막에 live_save 한 번으로 끝납니다. 제목 표시줄의 점이 사라지고 디스크의 파일이 화면과 같아집니다. 에이전트가 live_new_project로 시작한 프로젝트까지, Mac의 모든 프로젝트는 처음부터 파일이 있으므로 저장 위치를 먼저 고를 필요가 없습니다.

4. 처음부터 만들기

“porcelain 테마로 iPhone 5장짜리 프로젝트 만들고 이 문구들 넣어 줘.” live_new_project 다음 live_patch가 이어집니다. 스크린샷은 직접 넣으셔야 합니다 — 에이전트에게는 파일 접근 권한이 없습니다.

스위치

헤더 카드에는 켜고 끄는 스위치가 있고, 끄면 실제로 꺼집니다. 소켓이 삭제되고 아무것도 대기하지 않습니다. 이 선택은 다음 실행에도 유지되므로, 꺼 둔 브릿지는 앱을 켠 첫 순간부터 꺼져 있습니다 — “창이 다 뜰 때까지는 켜져 있다”가 아닙니다. 다시 켜는 것도 같은 자리입니다.

포트가 아니라 소켓인 이유

앱은 127.0.0.1:포트가 아니라 사용자 홈의 Library 폴더 안에 있는 유닉스 도메인 소켓(권한 0600)에서 대기합니다. 브라우저 안의 웹 페이지는 유닉스 소켓을 열 수 없습니다. 그래서 어쩌다 방문한 페이지가 파일을 쓰는 데스크톱 앱을 조용히 조종하는 부류의 공격이 통째로 사라집니다. 소켓 경로는 디버깅용으로 카드 안에 있지만, 연결할 때 그 경로를 알 필요는 없습니다.

아무것도 Mac을 떠나지 않습니다. 에이전트는 앱과 이야기하고, 앱은 로컬에서 프로젝트를 고칩니다.

파일 기반 방식

열린 앱을 조종하는 것이 한 가지 방법이고, 다른 하나는 파일입니다. 저장소를 체크아웃하면 같은 MCP 서버가 파이프라인 도구까지 제공합니다 — 작성한 폴더를 최종 PNG로 렌더링하고, 저장된 .studio.zip을 무손실로 수정하고, 레이아웃 자동 교정 루프를 돌립니다. CI나 여러 릴리스를 한꺼번에 처리할 때 쓰는 방식입니다. op 어휘는 어느 쪽이든 같습니다.

FAQ

스크린샷이 어딘가로 업로드되나요?
아니요. MCP 서버는 내 컴퓨터에서 실행되고 로컬 소켓으로 앱과 통신합니다. 앱에는 백엔드가 없습니다 (개인정보 처리방침 참고).

API 키가 필요한가요?
아니요. 지능은 사용자의 MCP 클라이언트 쪽에 있고, 앱은 모델도 키도 갖고 있지 않습니다.

Windows나 Linux는요?
데스크톱 앱이 현재 macOS 전용이라 live 도구도 macOS 전용입니다.

에이전트가 제 다른 파일을 볼 수 있나요?
아니요. 브릿지는 열린 프로젝트에 대한 정해진 어휘만 주고받습니다. “이 파일을 읽어라” 같은 호출은 아예 없고, 디스크의 이미지를 끌어오는 op는 live 경로에서 거부됩니다.
